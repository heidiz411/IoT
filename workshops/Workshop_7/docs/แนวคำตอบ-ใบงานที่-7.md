# แนวคำตอบและหมายเหตุสำหรับอาจารย์ผู้สอน — ใบงานที่ 8 (ฉบับ Wokwi + VS Code)

คณะเทคโนโลยีสารสนเทศ มหาวิทยาลัยราชภัฏร้อยเอ็ด · จำนวน 120 นาที

---

## ข้อผิดพลาดที่พบในใบงานต้นฉบับ และการแก้ไข

| ประเด็น | ต้นฉบับ | ฉบับนี้ |
|---|---|---|
| `#include <ESP8266WiFi.h>` | มีอยู่ในโค้ด 8.1 ทั้งที่ไม่ได้เรียกใช้เลย | ตัดออก (ใช้กับ ESP32 ไม่ได้ คอมไพล์ไม่ผ่าน) |
| ค่าเกณฑ์แก๊ส | `ValuaBegin = 300` (สเกล 10 บิต) | ปรับเป็น 1200 (12 บิต) |
| ข้อความงานที่มอบหมาย 6.5 | เขียนว่า `int ValuaBegin = 200` | ไม่ตรงกับโค้ดจริงที่กำหนด 300 — แก้ข้อความให้สอดคล้อง |
| พัลส์กระตุ้น TRIG | `delayMicroseconds(5)` | แก้เป็น 10 µs ตามที่คู่มือ HC-SR04 กำหนด |
| `pinMode()` ของ 8.2 | เรียกอยู่ภายใน `loop()` ทุกรอบ | ย้ายไปไว้ใน `setup()` |
| การแสดงผล 8.1 | ใช้ `Serial.print()` ทั้งสองบรรทัด ไม่ขึ้นบรรทัดใหม่ | เปลี่ยนบรรทัดค่าเป็น `Serial.println()` |
| หัวข้อ 6.4 การทดสอบ | ทดสอบด้วยแก๊สจากไฟแช็ก | เปลี่ยนเป็นการเลื่อนแถบ ppm ในโปรแกรมจำลอง |
| บอร์ด | NodeMCU (ESP8266) | ESP32 DevKit V1 — Wokwi ยังไม่รองรับ ESP8266 |
| Serial | 9600 | 115200 ให้ตรงกับ `monitor_speed` |

**ประเด็นความปลอดภัยที่ต้องย้ำก่อนนักศึกษาย้ายไปบอร์ดจริง**

1. MQ-2 ของจริงต้องใช้ไฟ 5V สำหรับฮีทเตอร์ และแรงดันที่ขา AO อาจถึง 5V — ต้องผ่านวงจรแบ่งแรงดันก่อนเข้า ADC ของ ESP32 ที่รับได้ไม่เกิน 3.3V (ในโปรแกรมจำลองเลี้ยงด้วย 3V3 จึงปลอดภัย)
2. ขา ECHO ของ HC-SR04 ส่งสัญญาณ 5V TTL เช่นกัน ต้องแบ่งแรงดัน (เช่น 1kΩ + 2kΩ) ก่อนเข้า GPIO
3. ต้องใช้ขาในกลุ่ม ADC1 (GPIO32–39) เท่านั้นถ้าจะเปิดใช้ WiFi ในภายหลัง

## แนวคำตอบข้อ 9

**9.1** คู่มือของ HC-SR04 กำหนดให้พัลส์กระตุ้นกว้างอย่างน้อย 10 ไมโครวินาที เพื่อให้วงจรภายในโมดูลตรวจจับขอบสัญญาณได้แน่นอนและเริ่มส่งชุดคลื่นเสียง 40 kHz ออกไป ถ้าพัลส์แคบกว่านั้น โมดูลอาจไม่เริ่มวัดค่า ขา ECHO จะไม่มีพัลส์ตอบกลับ `pulseIn()` จะคืนค่า 0 (หรือรอจนหมดเวลา) และโปรแกรมจะแสดงระยะทางเป็น 0 ตลอด

**9.2** ความเร็วเสียงในอากาศประมาณ 340 เมตร/วินาที คิดเป็นประมาณ 29 ไมโครวินาทีต่อ 1 เซนติเมตร การหารเวลาด้วย 29 จึงได้ระยะทางเป็นเซนติเมตร แต่เวลาที่วัดได้คือเวลาที่คลื่นเดินทาง **ไปและกลับ** จึงต้องหารด้วย 2 อีกครั้งเพื่อให้ได้ระยะทางเที่ยวเดียว (รวมแล้วเท่ากับหารด้วย 58 ตามคู่มือของ Wokwi)

**9.3** `pulseIn(pin, HIGH)` จะรอจนขาสัญญาณเปลี่ยนเป็น HIGH แล้วเริ่มจับเวลา และหยุดจับเมื่อกลับเป็น LOW คืนค่าเป็นไมโครวินาที ถ้าไม่มีสัญญาณสะท้อนกลับมาเลย ฟังก์ชันจะรอจนครบเวลา timeout (ค่าปริยาย 1 วินาที) แล้วคืนค่า 0 ระหว่างนั้นโปรแกรมทั้งหมดจะหยุดรอ ทำให้ระบบไม่ตอบสนอง — แก้ได้โดยกำหนด timeout เอง เช่น `pulseIn(inPin, HIGH, 25000)`

**9.4** MQ-2 : แก๊สยิ่งมาก → แรงดันที่ขา AO ยิ่งสูง → ค่าที่อ่านได้ยิ่งมาก จึงใช้เงื่อนไข `>` ส่วน LDR ในใบงานที่ 6 : ยิ่งสว่าง → ค่าที่อ่านได้ยิ่งน้อย ทิศทางจึงตรงข้ามกัน ทั้งนี้ขึ้นกับว่าตัวเซนเซอร์อยู่ฝั่งใดของวงจรแบ่งแรงดันภายในโมดูล

**9.5** เพราะขา ADC และ GPIO ของ ESP32 รับแรงดันได้สูงสุด 3.3 V ขณะที่โมดูลทั้งสองทำงานที่ระดับ 5V TTL หากต่อตรงจะทำให้ขาสัญญาณเสียหายถาวร วงจรแบ่งแรงดันช่วยลดระดับแรงดันลงมาให้อยู่ในพิกัดที่ปลอดภัย

**9.6** ทั้งสองโปรแกรมใช้ `delay()` (500 ms และ 200 ms) ซึ่งหยุดการทำงานทั้งหมด ถ้ารวมกันในโปรแกรมเดียว เซนเซอร์แต่ละตัวจะถูกอ่านช้าลงและอาจพลาดเหตุการณ์สำคัญ เช่น แก๊สรั่วในช่วงที่กำลังรอวัดระยะ แก้ไขโดยใช้ `millis()` จับเวลาแยกกันสำหรับแต่ละงาน (แนวคิดเดียวกับใบงานที่ 6 ข้อ 12.2) หรือใช้ FreeRTOS task แยกกันบน ESP32

## แนวคำตอบงานที่มอบหมายข้อ 7.6

เมื่อลดค่า `ValuaBegin` ระบบจะแจ้งเตือนที่ระดับ ppm ต่ำลง (ไวขึ้น แต่เสี่ยงแจ้งเตือนผิดพลาด) เมื่อเพิ่มค่า ระบบจะต้องมีแก๊สเข้มข้นมากขึ้นจึงจะแจ้งเตือน (ปลอดภัยจากการเตือนผิด แต่เสี่ยงตรวจไม่พบเหตุจริง) นักศึกษาควรสรุปได้ว่าค่าเกณฑ์คือการแลกได้แลกเสียระหว่าง **false alarm** กับ **missed detection**

## แนวคำตอบงานที่มอบหมายข้อ 8.6 (เซนเซอร์ช่วยจอดรถ)

เพิ่มบัซเซอร์ที่ GPIO5 ไม่ได้เพราะขานั้นถูกใช้เป็น TRIG แล้ว ให้ย้ายบัซเซอร์ไปขาอื่น เช่น GPIO18 และ LED ที่ GPIO16

```cpp
#include <Arduino.h>
const int pingPin = 5;    // TRIG
const int inPin   = 4;    // ECHO
const int LED     = 16;
const int BUZZER  = 18;   // ย้ายมาจาก GPIO5 เพราะขานั้นใช้เป็น TRIG แล้ว

unsigned long lastBeep = 0;

long readCm() {
  digitalWrite(pingPin, LOW);  delayMicroseconds(2);
  digitalWrite(pingPin, HIGH); delayMicroseconds(10);
  digitalWrite(pingPin, LOW);
  long d = pulseIn(inPin, HIGH, 25000);   // timeout 25 ms ~ 400 cm
  return d / 29 / 2;
}

void setup() {
  Serial.begin(115200);
  pinMode(pingPin, OUTPUT);
  pinMode(inPin, INPUT);
  pinMode(LED, OUTPUT);
  pinMode(BUZZER, OUTPUT);
}

void loop() {
  long cm = readCm();
  Serial.print(cm); Serial.println(" cm");

  unsigned long interval;                 // ช่วงห่างของเสียงเตือน
  if (cm > 100 || cm == 0) {              // ไกล หรือวัดไม่ได้
    digitalWrite(LED, LOW);
    interval = 0;                         // ไม่ต้องเตือน
  } else if (cm >= 20) {
    digitalWrite(LED, HIGH);
    interval = 600;                       // จังหวะห่าง
  } else {
    digitalWrite(LED, HIGH);
    interval = 120;                       // ถี่ขึ้นอย่างชัดเจน
  }

  if (interval > 0 && millis() - lastBeep >= interval) {
    lastBeep = millis();
    tone(BUZZER, 2000, 60);
  }
  delay(50);
}
```

ถ้าต้องการให้จังหวะเสียงไล่ระดับอย่างต่อเนื่องแทนการแบ่งเป็นสามช่วง ใช้ `interval = map(constrain(cm, 20, 100), 20, 100, 120, 600);` แทนบล็อก if–else ได้ (เป็นคำตอบระดับดีมาก)

**จุดที่ควรตรวจ**

1. ย้ายขาบัซเซอร์ออกจาก GPIO5 หรือไม่ (ถ้ายังใช้ขาเดียวกับ TRIG จะทำงานผิดพลาด)
2. จัดการกรณี `pulseIn()` คืนค่า 0 (วัดไม่ได้) แยกจากกรณี "ใกล้มาก" หรือไม่ — นี่คือกับดักที่นักศึกษาส่วนใหญ่พลาด เพราะ 0 จะเข้าเงื่อนไข "น้อยกว่า 20" ทำให้บัซเซอร์ร้องถี่ตลอดเวลา
3. ใช้ `millis()` คุมจังหวะเสียง ไม่ใช่ `delay()` ยาว ๆ

## ผลที่ควรได้ในตารางบันทึกผล

**ข้อ 7.5 (แก๊ส)** ค่าที่อ่านได้จะเพิ่มขึ้นตามค่า ppm ที่ตั้ง ให้ตรวจแนวโน้มและจุดที่ระบบเริ่มแจ้งเตือน (ค่าที่อ่านได้เกิน 1200) ไม่ต้องยึดตัวเลขตายตัว เพราะขึ้นกับวิธีจำลอง ADC ของ Wokwi และแรงดันเลี้ยงที่ใช้

**ข้อ 8.5 (ระยะทาง)** ค่าที่แสดงควรใกล้เคียงกับระยะที่ตั้งไว้ โดยมีความคลาดเคลื่อนเล็กน้อยจากการหารแบบจำนวนเต็ม (integer division) — ถ้านักศึกษาถามว่าทำไมได้ 99 แทน 100 ให้ชี้ว่า `long` ตัดเศษทศนิยมทิ้ง และให้ลองเปลี่ยนเป็น `float` เทียบดู
